## 已验证行为

1. fresh 首先保存正文，再检查当前 seat、busy、草稿和未完成输入。非空白与空白草稿均受保护；未知、错误或身份不匹配的检查结果也排队。
2. 只有事务提交 RESET_REQUESTED 的调用者可 reset。ResetRequest 不携带工作正文，包含冻结角色正文、prompt_file 来源路径、cwd、权限/参数和 `<context_dir>/<run_id>`；原提示文件删除后仍使用冻结正文。
3. adapter 返回的新 native session/thread 必须不同于旧值及历史绑定，workspace/surface 保持原目标；独立 READY 的 run/agent/下一 generation/tool/native/status 全部匹配后，才原子推进 current seat、generation 与原 delivery 目标。
4. persistent 保留当前 native/generation；两种模式在提交正文前都检查输入。普通 send 仅保存补充，不调用 reset、inspect、READY 或 submit adapter。
5. 正文调用前提交 SUBMIT_REQUESTED、attempt=1，匹配的 adapter 接收证据记录 SENT/channel。ACK 只表示接收；精确关联当前工作的 DONE/FAILED/BLOCKED_CONFIRM 报告释放 BUSY/current_message_id。非终态报告或修改重复 reply 请求中的 status 不释放工作。
6. 队列按已保存顺序推进。尚未 reset 的消息可在上一工作结束后定位当前代际；READY 后出现草稿只排队正文，继续时不再 reset。
7. reset 错误、相同 native、其他 surface、缺失/旧代际/错误 READY、取消、投递错误或不匹配证据均保留原请求阶段。重开数据库、并发请求和重复 request_id 不重复 reset 或重发正文。未知前项阻止后项绕过队列。
8. 旧 generation 的 READY、ACK、结果和无 READY 的 fresh ACK/结果被拒绝。sender 在观察后换代也无法取得动作门禁。相同 request_id 保留首次模式，正文不同返回 IDEMPOTENCY_CONFLICT。
9. reset 确认在 seat/delivery/journal 各处失败全部回滚；submit 确认失败不留下部分 SENT/BUSY 状态。多 Store 句柄的并发门禁只授权一次原生动作。

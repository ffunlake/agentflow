# S5.3 持久化对账与恢复决策结果

日期：2026-11-03。任务：`s5-reconcile-recovery`；协作 session：`55cfdc22-9623-4ef5-aab2-131507069c27`。

状态：**最小 store/runtime API、决策查询 CLI 与本地故障验证 PASS；真实工具恢复保持 PARTIAL / UNVERIFIED**。

本轮使用现有五张业务表、schema v1 和 append-only journal 实现恢复前的持久化对账。没有增加依赖或 tasks 表。对账成功表示决策已持久化或查询完成，不能作为原生工具已恢复的证据。

## 实现与契约

- [store/reconcile.go](../../internal/store/reconcile.go)：`ReconcileSession(ctx, originalSender, messageID)` 在同一事务读取 delivery/reset/submit、journal、当前 seat generation/tool/native/workspace/surface、busy/current work 与 stop intent。`RecoveryDecision` 包含 `state/reason/next_action`、delivery、当前绑定、`stop_requested/evidence_seq/journal_seq/recorded_at`。
- `SAFE_TO_CONTINUE` 只表示持久账本没有阻止继续；下一动作 RESET/SUBMIT 仍需 runtime 重新检查输入并通过排他动作门禁。QUEUED 保留草稿、忙碌、前序工作、adapter 等阻塞原因。缺失原生动作结果或 delivery/journal 矛盾输出 `UNKNOWN_NEEDS_RECONCILE`；已开始动作的旧目标输出 `REJECTED_OLD_GENERATION`。已确认 SENT/ACKED 读取匹配 journal 后返回，不再执行。
- 只有协调派发处于 QUEUED、reset NONE、attempt=0 且没有任何原生动作 journal 时，才能安全定位当前 generation。`SESSION_RELOCATED`、delivery 更新与 `SESSION_RECONCILED` 原子提交；停止意图阻止重新定位和原生执行。PENDING 旧目标、READY 和所有已开始动作的目标保留。
- `SESSION_RECONCILED.details` 保存决策内容。相同证据重查复用最新决策的序号和时间，跨数据库重开和多 Store 句柄并发保持一致；状态或证据变化追加新决策。对账记录本身不导致下次重复追加。
- [store/session.go](../../internal/store/session.go)：动作门禁同时检查历史 reset/submit/sent/acked journal、attempt 与 READY 确认，防止仅把 delivery 改回 QUEUED 就重新执行。stop 与换代并发时，最终事务仍阻止动作及目标代际移动。请求阶段不清除，不增加第二次尝试。
- [runtime/reconcile.go](../../internal/runtime/reconcile.go)、[runtime/session.go](../../internal/runtime/session.go)：`SessionCoordinator.Reconcile`、`MessageService.Reconcile/Resume` 不调用 adapter。`Advance` 和重复 assign 在任何原生动作前先持久化对账；未知、已完成、旧目标和 stop intent 不进入原生路径。READY 后继续只提交正文，不再次 reset。
- [store/messaging.go](../../internal/store/messaging.go)：历史代际 ACK/reply 与 reset/submit 确认拒绝后，事务追加去重 `SESSION_RESULT_REJECTED` 并返回原身份错误；不改变 delivery、current seat 或保存报告正文。未知 agent、跨 run 和非原 recipient 不得到该审计身份。
- [CLI](../../internal/cli/messages.go)：`reconcile|resume <message-id> --run ID --agent ID --generation N [--run-dir DIR] [--json]`，两者为同义决策查询，不需要 request ID。输出 `status=RECONCILED`、`executed=false`、`runtime_communication=UNVERIFIED`；UNKNOWN/QUEUED/旧目标决策持久化成功仍退出 0。身份、记录缺失和存储失败退出 1，参数错误退出 2。不迁移或创建数据库。

## 故障验证与证据

| 场景 | 实际验证结果 |
|---|---|
| 消息事务提交后响应丢失、同 request 重试 | 原消息和路由复用；仍执行持久化对账，不创建第二项原生请求 |
| RESET_REQUESTED 后中断，尚未写未知诊断 | 重开数据库得到 UNKNOWN_NEEDS_RECONCILE，目标/attempt 保留，不重复 `/new` |
| reset 响应丢失或 READY 缺失 | 保留请求阶段；重启后 Reconcile/Resume/Advance/assign 均不调用 reset/submit |
| READY 已确认、提交尚未开始 | READY 与绑定保留；重启后显式 Advance 只提交一次，不再 reset |
| SUBMIT_REQUESTED 后中断或响应丢失 | 重开后 UNKNOWN，attempt=1，不自动重发正文 |
| SENT/ACKED 已确认 | 返回原提交/接收状态，不再次执行；缺少匹配 journal 的伪终态保持 UNKNOWN |
| 未开始动作的 QUEUED 项换代 | 安全重新定位并追加一次 relocation/decision；PENDING、requested、READY 和带历史动作的项禁止移动 |
| delivery 行回到 QUEUED，但 journal 已有请求 | 对账保留 UNKNOWN，动作门禁不能领取第二次执行 |
| 旧代际 ACK/reply/reset/submit 迟到 | 拒绝并记录去重审计；不创建结果消息、不释放当前 seat、不改变 delivery |
| 对账 journal 插入失败 | delivery 重新定位及 relocation event 全部回滚，无半提交 |
| 并发 Store 句柄与数据库重开 | 返回相同 journal_seq/recorded_at，无重复决策凭据 |
| stop 与重新定位/执行边界竞争 | 不执行原生动作、不移动目标；stop intent 可在决策中读取 |
| CLI 跨进程 reconcile/resume | JSON 决策一致；ACKED、QUEUED、reset/submit 中断均验证成功 |

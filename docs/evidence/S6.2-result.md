## 核心契约

报告位于 `<context_dir>/<run>/<agent>/.reports/g-<generation>/<report_id>/`，证据位于同 agent 的 `.evidence/g-<generation>/`。目录 0700，文件 0600；临时文件 fsync 后 hard-link 原子无覆盖发布，manifest 最后提交，读回核对版本、身份、路径、SHA、权限和完整文件。相同 report/request 标识返回 ErrExists，失败保留不可覆盖的未提交占位；不同 run/agent/generation 不能互相写入或借用证据。

Report 绑定 run/agent/generation/report_id，status 仅为 DONE/FAILED/BLOCKED_CONFIRM；summary/next 各最多 2048 字节，必填 1–8 个证据引用，证据非空且每份最多 128 KiB。可选 message_id/request_id 指原 lead 派发；request_id 是该派发原始请求 ID。只提供 request 时按 lead/recipient/request 查找，两者同时提供必须匹配。拒绝错误 author、旧/未来代际、未知/错误接收者消息、未 READY 的 fresh 派发、损坏/缺失/公开/链接证据及跨身份/越界路径。

Merge 只读验证明确选择的报告，在 lead 的新 revision 中保存状态、摘要、证据引用/SHA、源报告 SHA 与 next。原报告、旧 lead revision 和证据不被覆盖；证据、派发、prompt 正文不进入主摘要。输出固定 `verification=INTEGRITY_VERIFIED`、`meaning=agent_claim`，没有 PASS/自动验收字段。每批最多四份且受原 Section 的 8192 字节/16 引用限制，超限整体拒绝。S5 ACK、delivery、seat 和 journal 继续由现有消息 API 管理。

## 限制与下一步

身份校验是同一 OS 用户下的 API 能力边界，SHA 用于检测损坏；恶意同用户进程和传输身份认证不由本轮解决。调用方负责提炼 summary 和选择允许保存的证据。报告历史可通过文件层显式审计；runtime 只接受当前代际参与工作流。

文件与 SQLite 不具备跨介质原子回滚，commit/进程中断可能留下已发布文件或未提交占位；重复标识明确拒绝，后续应读回核对。未增加自动清理、恢复、依赖、schema 或 CLI，也未启动真实原生工具、工作区或修改 wiki。

下一步由主 agent 独立复核本轮 API 与证据，随后决定真实工具注入及 S6.3 会话重建的范围。handoff 使用现存 `okra-agent-init/scripts/agent-handoff.sh`，因为全局 `agent-handoff` 启动器引用的旧脚本已不存在；只使用既有指定路由。

# AgentFlow 访谈结论与决策记录

日期：2026-11-02。状态：用户已在 Q18 明确回复“确定”。

本文记录本次 grill-me 访谈的最终结论。它是后续修订架构、技术实现和实施计划的需求依据。本文不代表程序已实现、工具接入已验证或权限设置已实际执行。

## 1. 产品目标

构建一个接近 agent-init 基本协作能力的轻量工具：通过 YAML/JSON 定义角色与嵌套分屏，使用命令在 cmux 中启动多个 agent，支持稳定通信，并由主 agent 自主组织工作。

首版同时支持 OpenCode、Codex、Claude Code。用户在终端工作，每个分屏保留对应工具的原生交互界面。

## 2. 角色与职责

| 参与者 | 已确认职责 |
|---|---|
| 用户 | 提出目标、配置团队、随时在原生终端补充指令或停止成员 |
| 主 agent | 判断工作可行性、维护精简文件上下文、分配工作、核实结果并决定下一步 |
| 执行者 | 读取必要输入、执行工作、保存产物、完成验证、写独立结果报告并回报 |
| AgentFlow | 启动成员、编排分屏、路由消息、确认接收、观察状态和恢复运行 |

主 agent 是 AI 会话；协调进程是普通程序。需求是否可实现由主 agent 判断，程序检查工具、登录、权限、工作目录和通信等运行条件。

## 3. 配置与终端

- YAML 和 JSON 均可定义角色、职责、工具、工作目录及嵌套分屏。
- 第一期终端后端只支持 cmux。
- 首版的工具范围包含 OpenCode、Codex、Claude Code，不能仅完成 OpenCode 就宣布全部完成。
- 运行使用启动时的配置快照。修改配置在下一次启动生效；恢复原运行继续沿用原配置。
- 消息接收和工作执行必须发生在用户分屏正在展示的同一个会话中。
- 后台可以使用本机服务或 API，但不能让隐藏会话替可见会话工作。
- 用户可以直接与任意成员交互。消息投递和会话重置必须保护正在编辑的输入。

## 4. 默认权限与自主推进

用户明确要求：“默认开启最高权限”。权限模式用于本次启动的会话；具体启动参数和配置方式须按各工具实际能力验证。

工作条件和可行性确认后，正常的实现选择、验证、修复与恢复由 agent 自主决定，不逐步请求用户确认。

用户对连续运行的要求是：一旦开放最高权限、确认工作可行，工作流应持续自主推进。

经进一步确认，其具体含义为：

- 可恢复故障自动处理，例如重连、等待限流恢复、恢复会话和核对已有产物。
- 不因普通错误或固定重试次数用尽就直接终止工作流。
- 依赖暂不可用时保留待恢复状态，依赖恢复后自动继续。
- 缺少必须的外部输入、登录或额度时，通知用户并保留上下文。
- 对无法确认是否已执行的操作先核对，不为保持运行而盲目重复执行。
- 默认沿用角色配置的工具、模型与账号；只有明确配置备用项时才自动切换。

“保持运行”不等于持续无效调用模型，也不表示可以保证所有外部依赖始终可用。

## 5. 执行者会话策略

### 5.1 默认行为

用户对长期会话的顾虑是上下文膨胀。最终确认：执行者默认每次新工作开启新会话，同时支持持续会话配置，便于实际比较效果。

主 agent 派发下一项工作时，直接让执行者开启新会话，再发送工作内容。工具可使用 /new、/clear 或等价接口；每个工具的具体方式需验证。

主 agent 的关键要求是通过精简文件维护可恢复上下文；不要求依赖无限增长的聊天历史。

### 5.2 新工作与补充说明

- 下一项新工作：fresh 模式重置会话，重新提供角色与必要文件上下文。
- 当前工作的补充、追问或修正：继续进入当前会话。
- persistent 模式：新工作也可继续使用原会话。
- 重置完成后必须验证实际会话和消息路由已切换，不能仅假设命令已生效。

### 5.3 用户明确要求的简化

用户原话：“不需要那么复杂，主agent直接分配下一个任务，就直接开启新会话”。

因此首版不要求用户或主 agent 操作独立工作 ID、领取凭证、任务领取或强制验收状态机。一次派发操作应完成必要的会话重置与发送。

内部消息 ID、接收确认、会话绑定和恢复日志仍可存在，但它们服务于通信可靠性，不扩展成任务管理系统。

## 6. 文件上下文与报告

主 agent 统一整理精简的共享上下文，至少覆盖项目背景、已确认决策、当前进度及未完成事项。

执行者读取本次工作所需文件，写独立结果报告；主 agent 核实后提炼合并。执行者不共同改写一份共享摘要。

详细日志、测试输出和原始证据独立保存，通过路径引用。新会话读取必要文件，不复制全部聊天历史。

具体目录、文件名和摘要大小属于实施选择；尚未在访谈中确定固定数值。

## 7. 同一工作中断后的恢复

“新工作用新会话”和“故障恢复”是不同场景。

同一工作因断线或进程故障中断时，优先恢复原会话和执行进度。原会话无法恢复时，读取检查点并核对实际产物，再创建替代会话继续剩余工作。

保留原会话与证据的关联。不能因为重新建立会话就从头执行整项工作。

## 8. 完成、待命与停止

用户以 agent-init 的行为明确了完成语义：“执行完就等待下次工作分配就好了”。

执行者完成、验证、回报结果后待命。主 agent 检查结果并决定是否修正或继续派发。没有强制 task accept 操作。

成员 idle 只是空闲观察，不单独证明总目标已经完成。

用户主动退出原生 agent 或关闭对应分屏，视为停止该成员；系统通知主 agent，不自动重新打开。程序意外崩溃或通道断线则进入自动恢复。

如何可靠区分主动退出和意外崩溃属于实施验证项。

## 9. 工作目录与协作范围

首版允许多个成员共享一个项目目录，由主 agent 划定修改范围。暂不自动创建 Git worktree，也不自动合并代码。

消息通道稳定不等于文件修改自动隔离。通过分工避免同时修改同一文件，发生冲突时由主 agent 协调。

## 10. 对原计划的修订要求

| 原计划约定 | 最终修订方向 |
|---|---|
| 第一条完整交付主要围绕 OpenCode | 首版范围同时覆盖三个工具，接入验证提前覆盖全部工具 |
| Codex 仅作为延迟接收工具 | 验证主动接收和同会话唤醒路径；不能以延迟接收代替首版完整支持 |
| 自动重试一次后转交人工 | 可恢复故障自动处理，依赖暂不可用时等待恢复后继续 |
| 执行者默认长期会话 | 默认新工作新会话，并支持持续会话配置 |
| 上下文主要依赖会话历史 | 主 agent 维护精简文件，执行者按需读取 |
| 独立任务领取、凭证与强制验收流程 | 删除这层产品流程；主 agent 直接派发并检查结果 |
| 故障后主要等待用户恢复 | 优先自动核对、恢复原会话或按检查点继续 |
| 权限模式未明确 | 默认最高权限，启动时正确配置并验证有效状态 |

## 11. 已知事实与待验证方案

本机只读检查发现 Codex 0.166.0 提供 queue --resume、app-server 和原生 TUI 的远程连接选项。queue --resume 恢复失败时仍可能成功退出，因此命令退出码不能证明已经唤醒会话。

候选接入方式：OpenCode 的服务与 session API；Codex 的原生队列或 app-server；Claude Code 的 cmux 消息 hook。它们是实现候选，不是已经通过验收的结论。

三个工具都需要实际验证：原生界面与接收会话一致、空闲接收、新会话重置、角色重新注入、权限生效、故障恢复，以及用户输入不被破坏。

精确 CLI 名称、数据库结构、重试间隔、会话模式字段名称和文件目录结构由技术实现文档确定。不能把这些工程选择写成用户在访谈中要求的固定方案。

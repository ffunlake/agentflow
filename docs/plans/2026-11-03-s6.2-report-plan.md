# S6.2 执行者独立报告与主 agent 精简合并实施计划

任务：`s6-report-merge`；session：`237abea2-c48b-4846-8217-a8e6b4f35ed8`。

## 目标与设计

延续 S6.1 的身份绑定目录、0700/0600、不可变版本、临时文件/fsync/hard-link 无覆盖发布和 manifest 最后提交。每 agent 增加 `.reports/g-N/report-id/` 与 `.evidence/g-N/`，避免与原 revision 命名空间冲突。报告只保存状态、摘要、证据路径/SHA 和下一步，显式绑定 run/agent/generation/report_id；可选 message/request 关联原始派发。拒绝空/超限正文、缺证据、越界引用和损坏。

选择独立文件 API + 现有 SQLite 事务门禁：相较直接扩展 S5 消息正文，报告具备独立、不可变产物且不复制完整聊天；相较新增表/协调服务，无需依赖或 schema。文件层检查身份和完整性，runtime 通过 Store.WithReportContext 在 immediate 事务内检查冻结配置/lead、当前 actor/author 和可选原派发关联，并覆盖实际文件操作，避免代际竞态。

request_id 明确定义为原始 lead → author 的 assign/send request；单独提供可查找，同时提供 message_id 时必须匹配。重复 report/request 明确 ErrExists，不覆盖。失败可留未提交目录或 request 占位，显式读回、人工决定后续，不实现自动恢复。报告不自动 ACK 或释放 S5 seat，已有 MessageService 继续管理消息状态。

主 agent Review/Merge 只接受报告引用，读取并验证原报告和证据，状态保持 agent_claim；验证结果只为 INTEGRITY_VERIFIED。合并到自己的显式新 revision：保留协议/背景/决策，本批摘要/状态/证据引用替换 progress，next 替换 pending；不复制证据、派发或 prompt 正文。每批 1–4 份且仍受原 Section 上限约束；原报告、证据与旧主 revision 均不可变。

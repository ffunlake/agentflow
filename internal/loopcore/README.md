# Minimal workflow loop core

`loopcore.Advance(workflow, lead, cursor, event)` is deterministic and performs no I/O. It returns a detached cursor and zero or one dispatch intent. `build_review` preserves execute→review, with the reviewer submitting the approval/changes result. `approval` assigns an approver per work step; an approver may return work to the current or an earlier step, with reason and per-step visit limits persisted in the cursor. A seat may execute one step and approve another, but cannot approve its own work in the same step. `pipeline` walks the configured `lead -> role... -> lead` route, passing each handoff to the next role and returning the final handoff in the completed cursor. Pipeline route length is configuration-driven. `store.AdvanceWorkflow(ctx, MessageActor, Event)` authenticates the current seat, loads the frozen run configuration, verifies its digest, and commits the intent and cursor in one SQLite transaction. Callers must authenticate their transport before using the store API.

The initial event is `start`, with revision 0 and the frozen lead as actor. It dispatches the entry step to its executor. Every dispatch body is JSON `loopcore.Intent`, including revision, step, attempt, purpose (`execute` or `review`), instruction, acceptance criteria, required handoff, and prior handoff/rework reason where applicable. The returned message ID is the next cursor's `dispatch_id`.

Subsequent events provide a stable unique ID, the expected cursor revision, actor and dispatch message ID. A formal executor `handoff` must include nonempty summary, evidence references and next action. It dispatches a separate review; the handoff itself does not approve the work. Only the configured reviewer can `approve`, with one explicit `true` judgment per acceptance criterion. Approval advances to `next` or the terminal completion marker.

In `build_review`, `changes` from the reviewer and `retry` from the current executor/reviewer repeat the same step with a new attempt. In `approval`, `changes` targets the configured current or earlier step; visits are counted per step across backtracking, so a return cannot reset its budget. In `pipeline`, `retry` repeats the current role. `blocked` pauses without dispatch. Only the frozen lead can `resume`, with a reason; resume starts a new execution attempt and consumes the saved budget. At the saved maximum attempts, changes/retry/resume enters `EXHAUSTED` without dispatch. A completed run may start another task at the entry/first role while keeping the revision monotonic; exhausted runs cannot restart. Blocked/changes/retry/resume require a nonempty reason.

The cursor is stored in each append-only `WORKFLOW_ADVANCED` journal receipt; the latest receipt materializes the current state. One `BEGIN IMMEDIATE` transaction commits the dispatch message, target-generation delivery, dispatch journal, accepted input receipt and new cursor. There is no schema change. A failed write rolls everything back. Concurrent ticks serialize; exact event retries return the original result, including message and journal identities, even after database reopen. Reusing an event ID with different input/actor conflicts. New events must match the current revision and current dispatch; late results from obsolete seat generations are rejected. Run stop intent prevents new advancement while allowing exact committed retries to return their receipt.

The [coordinator IPC event flow](../coordinator/README.md#workflow-event-flow) now exposes lead `start/resume` controls and structured worker/reviewer `reply` events. `store.ReplyWorkflow` reuses ordinary reply authorization/persistence within the same transaction as the reducer, next outbox item and cursor receipt. A failed transition or write rolls back the reply too. Event IDs come from the IPC request ID and reserve the existing caller/request namespace with messages, ACKs and stop; changed event or reply input conflicts. Event IDs must also remain unique across the run, matching the original store tick contract. Dispatch request IDs `workflow:<revision>` are reserved under the lead, and collisions fail atomically.

Workflow CLI, foreground runner, headless adapters and a cmux OpenCode TUI adapter are available within their documented limits; there is no background scheduler. Handoff evidence and reviewer judgments are agent claims; the reducer validates structure and actor/revision/dispatch authorization, not evidence file contents. Native integration must authenticate its events. If a seat changes generation during an active stage, old results and automatic takeover/re-dispatch are rejected. Lead resume applies only to PAUSED and consumes the saved attempt budget.

Verification:

```sh
go test ./internal/loopcore ./internal/store ./internal/coordinator -run 'Test.*Workflow' -count=1
```

The fake three-role tests follow the configured example chain through both store and real local IPC: main → builder → reviewer; reviewer then executes the verification step and main reviews it to completion. Additional tests cover detached reducer outputs, explicit acceptance, finite rework, execution/review pause/resume, database/coordinator reopen, exact replay after stop, identical and competing different-event two-handle concurrency, invalid handoffs, terminal rejection, stale generation/revision, shared request namespace, strict nested params, frozen configuration tampering and injected reply/dispatch/cursor rollback failures.
